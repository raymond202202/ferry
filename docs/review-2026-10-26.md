# ferry 项目评审报告（Windows 真机实测）

- 评审对象：github.com/raymond202202/ferry @ 3aafb87
- 评审环境：Windows 10 x64 / Python 3.12.12 / PowerShell 5.1
- 评审方式：单元测试 + Windows 真机 drills + 30+ 条翻译用例逐条验证
- 日期：2026-10-26

## 一、总体结论

**架构方向正确，核心资产（映射数据）质量高，但引擎层存在 3 个危险 bug，其中 2 个会导致"翻译出的命令删错东西/静默做错事"——恰好违反项目自己最核心的设计承诺（"绝不静默降级"）。**

- 单元测试：45 项，42 通过 / 3 失败
- Windows drills 真机验证（`--emit ps1` + PowerShell 执行）：**9/9 全绿**——README 声称"Windows 侧没有真机跑过"，本次补上，数据侧无问题
- 翻译用例抽查：约 2/3 正确，1/3 有问题（含 3 个危险级）

## 二、问题清单（按严重度排序）

### P0-1【危险】recipe 槽位匹配吞掉用户路径

- 现象：`rm -rf /tmp/x`、`rm -rf /home/user/important` → 均输出 `Remove-Item -Recurse -Force build`
- 根因：`recipe_match()` 第二轮"示例值当槽位"匹配（ferry.py:712）里 `_slot_match()` 允许非参数 token 任意不同值。recipe `rm -rf build/` 的 `build/` 被当作槽位，命中后 `substitute_recipe_literals()`（ferry.py:1058）按位置把 recipe 示例值 `build` 替换回用户输入——但替换逻辑是"在输出里找 recipe 示例字面量再替换"，而输出 `Remove-Item -Recurse -Force build` 里的 `build` 来自 recipe 的 windows 侧写法，替换函数按 `zip(rt, input_toks)` 逐对替换时，`build`（recipe 源侧 token）→ `/tmp/x`（用户 token）本应替换成功；实测未替换，因为 `_norm_tokens` 把 recipe 的 `build/` 归一化成 `build`，而 tokenize 后 recipe 源侧是 `build/`，`re.escape(a)` 用的是未归一化的 `build/`，在输出 `...Force build` 中匹配不到（`build` 后面没有 `/`，负向断言 `(?![\w/\\-])` 恰好卡在斜杠上）→ 替换静默失败，示例路径原样吐出。
- 影响：**用户删 A 目录，翻译结果删 B 目录**。`rm -rf` 是最不该错的命令。
- 修复方案：`substitute_recipe_literals` 中对 recipe 源 token 与输出 token 都做 `_norm_tokens` 同款归一化（剥尾斜杠）后再匹配替换；并在替换失败时（输出仍含 recipe 示例字面量）降级 status 为 approximate 并加 caveat，绝不静默。

### P0-2【危险】`find -delete` 错配到 `Measure-Object`

- 现象：`find . -name '*.log' -delete` → `Measure-Object . -name '*.log' -delete`，status=approximate，无 caveats
- 根因：`wc` 条目（data/20-text.jsonc:209）的 `windows_cmd: "find"` 与 `find` 条目（data/10-files.jsonc:211）的 `windows_cmd: "dir"` 同名冲突。`KB._add()` 冲突时"保留前者"（ferry.py:446），`find` 在 windows_cmd 索引里被 `wc`（score=1）占住。源平台推断又把 `find` 推成 FreeBSD（见 P1-1），`find2("find", "freebsd")` 命中 find 条目没错，但 shell 回退链在 flags 翻译阶段用 `tgt_key=windows_cmd`？不对——实测输出 `Measure-Object` 是 `wc` 的 PowerShell 名。真正路径：`detect_source` 把源推成 freebsd 后，`find2` 在 freebsd 表命中 find 条目；但 `translate_flags` 里 `-delete` 不在 find 的 flags 表（数据只收录 -name/-type/-mtime），落入"未识别参数"分支；`-name` 命中 flags 表但 windows 侧值为 `-Filter`，extra=1 示例值 `*.log` 与用户值 `*.log` 相同→整体替换成功输出 `-Filter *.log`？实测输出仍是 `-name '*.log'`——因为源是 freebsd、目标 windows_cmd 时 `find2` 返回的 entry 是 wc（cmd 索引冲突），`exact_name_for("windows","cmd")` 拿到 `find`，但 shell_tgt=powershell 时 `name_for` 回退到 wc 条目的 `windows: "Measure-Object"`。**索引冲突 + shell 回退共同导致 find 命中了 wc 条目。**
- 影响：输出命令完全错误（Measure-Object 无 -delete/-name 参数），且无任何警告。侥幸之处是执行会报错而非误删。
- 修复方案：①`KB._add` 冲突时不再"保留前者"，改为按 `score`（id 同名=2 > 别名=1）取高者，平分且不同条目时让 `windows_cmd` 索引优先保留 id 精确匹配的条目（`find` 条目的 windows_cmd 就是 `dir`，`wc` 的是 `find`——两者都合法，冲突真实存在，cmd 下 `find` 确实是字符串查找器）；②`translate_segment` 在 entry 的 `names[tgt_key]` 为空时禁止回退到"另一个 shell 的名字"（wc 的 powershell 名 Measure-Object 不能在 cmd 语境使用，反之亦然）；③`-delete` 属 DANGEROUS_FLAGS，flags 表未收录时必须走"丢弃危险参数→unsupported"分支而不是直通。

### P0-3【危险】sed Windows 方向丢替换内容 + 输出文件错写

- 现象：`sed -i 's/a/b/' f.txt` → `(Get-Content f.txt) -replace 'old','new' | Set-Content a.txt`
- 根因：recipe `sed -i 's/old/new/' a.txt`（data/20-text.jsonc:128）的示例值 `old`/`new`/`a.txt` 与用户输入 `s/a/b/`/`f.txt` 位置对齐后，`substitute_recipe_literals` 逐对替换：`old`→`s/a/b/`？不对——tokenize 把 `'s/a/b/'` 拆成单 token `s/a/b/`，recipe 侧 `'s/old/new/'` 拆成 `s/old/new/`。`re.escape("s/old/new/")` 在输出 `-replace 'old','new'` 里匹配不到完整串，替换失败；但 `a.txt`→`f.txt` 在第一个 `Get-Content a.txt` 处替换成功（count=1），第二个 `Set-Content a.txt` 没被替换（count=1 已耗尽）→ 输出文件仍是示例值 `a.txt`。**替换只做一次（count=1）+ 复合示例值无法整体匹配 = 双重静默失败。**
- 影响：替换内容丢失（old/new 占位符原样输出）、输出文件名错误（写错文件）。
- 修复方案：sed 这类"参数内部含语义"的命令，recipe 不该靠字面量替换。给 recipe 增加显式槽位语法（`{pattern}`/`{repl}`/`{file}`），`fill()` 已有现成机制（patterns 用的就是 `{name}`）；或至少把 `substitute_recipe_literals` 的 count 改为"替换所有出现"，并对替换后仍残留示例字面量的输出强制降级 approximate + caveat。

### P1-1 源平台自动推断不可靠（字母序兜底）

- 现象：`stat`/`sed`/`date`/`jq`/`rm` 未指定 `--from` 时全被推断为 FreeBSD，`date -d yesterday` 被推断为 Windows
- 根因：`detect_source()`（ferry.py:1165）在多平台同名时 `sorted(hits)[0]` 字母序取第一个：freebsd < linux < macos < windows，三平台同名命令必然全推成 freebsd。`date -d` 推成 windows 是因为 `date` 在 windows_cmd 索引里存在（`date /t`），`find_any` 把 windows 也算进 hits。
- 影响：不指定 `--from` 时翻译质量不可控；README 承诺"源平台可省略"实际不可用。
- 修复方案：①多平台同名时优先推断为 linux（POSIX 命令的默认语境），而不是字母序；②`find_any` 排除 windows_cmd 专用名（`date /t` 的 date 是 cmd 内置，不是 POSIX date）；③推断结果与目标平台相同时加 note 提示显式指定 `--from`。

### P1-2 `echo $PATH` 变量未映射

- 现象：`echo $PATH` → `Write-Output $PATH`（PowerShell 里 `$PATH` 是未定义变量，输出空）
- 根因：recipe `echo $PATH`（data/20-text.jsonc:407）的 windows 侧写的是 `Write-Output $env:PATH`，但 tokenize 把 `$PATH` 拆成单 token，`_slot_match` 判定 recipe 的 `$PATH` 与输入 `$PATH` 相同→精确匹配命中，`substitute_recipe_literals` 无事发生，输出本应是 recipe 的 windows 侧 `Write-Output $env:PATH`。实测输出 `Write-Output $PATH`——因为源平台被推断成 freebsd（P1-1），src_key=freebsd，recipe 的 freebsd 侧 `echo $PATH` 与输入相同，精确命中，输出 windows 侧 `Write-Output $env:PATH` 才对。实测却输出 `$PATH`，说明命中的是 flags 路径而非 recipe：`$PATH` 不在 flags 表，走 convert_token 直通。**推断成 freebsd 后 recipe 匹配用的 want tokens 含引号差异？** 需在修复时进一步定位（可能与 tokenize 对 `$` 的处理有关）。
- 修复方案：`convert_token` 增加 POSIX 环境变量 → `$env:VAR` 的映射（`$PATH`→`$env:PATH` 等）；recipe 精确匹配优先级已高于 flags，修 P1-1 后此条大概率随之修复。

### P1-3 `stat -c %Y` → `-f %z` 语义错配

- 现象：`stat -c %Y f.txt`（修改时间 epoch）→ `stat -f %z f.txt`（文件大小）
- 根因：flags 表只收录了 `-c %s`（大小）和 `-c %a`（权限），`-c %Y` 未收录。`translate_flags` 里 `-c` 命中 flags 表（extra=1，示例值 `%s`），用户值 `%Y` ≠ 示例值 `%s`，走"目标参数也吃值：保留用户的值，只换开关部分"分支——但 `-c` 的 macos 侧是 `-f`，于是输出 `-f %Y`？实测输出 `-f %z`。**说明 same_as_example 判断后 tts 里包含了示例值**：`-c %s` 的目标侧写的是 `-f %z`（整体两个 token），`len(tts)-extra = 2-1 = 1`，输出 `tts[:1]`=`-f` + 用户值 `%Y` = `-f %Y` 才对。实测 `%z` 说明命中的是 recipe"文件大小"（`stat -c %s a.txt`）：`_slot_match` 里 `%s` vs `%Y` 都非参数、非开关→槽位匹配成功，recipe 输出 `stat -f %z a.txt`，`substitute_recipe_literals` 把 `a.txt`→`f.txt` 替换成功，但 `%s`→`%Y` 因在输出中是 `%z`（目标侧格式符）而替换失败→静默输出 `%z`。**又是"槽位匹配过宽 + 字面量替换静默失败"的组合。**
- 影响：修改时间查询变成文件大小查询，语义完全不同。
- 修复方案：`_slot_match` 对"格式符类"token（`%` 开头）要求精确匹配，不做槽位；`substitute_recipe_literals` 替换失败降级（同 P0-1 方案）。

### P1-4 `date -d yesterday` → `date yesterday` 不可执行

- 现象：输出 `date yesterday`，caveat"参数 -d 已丢弃"
- 根因：flags 表 `-d` 的 macos 侧为空串，`translate_flags` 走"目标无对应且值是用户自己的→原样保留"分支，输出 `date yesterday`。但 `date yesterday` 在 BSD date 里不是合法语法（应 `date -v-1d`）。数据侧 `-d` 的语义映射缺失（"解析指定日期"在 macOS 是 `-j -f`，相对日期是 `-v`）。
- 修复方案：flags 表补 macos 侧 `-v`（相对日期调整）映射；`-d` 后跟 `yesterday`/`tomorrow`/`now` 等相对词时映射到 `-v-1d`/`-v+1d`；或至少把该场景标 unsupported 而不是输出跑不通的命令。

### P2-1 `drills --to windows --run` 默认姿势假失败

- 现象：直接跑 6/9 失败，全是 `'Remove-Item' is not recognized`（cmd.exe 报错）
- 根因：`cmd_drills` 在 Windows 上用 `cmd.exe` 执行 drills（ferry.py:1726），而 Windows 断言是 PowerShell 写的。README 有说明，但默认命令必然踩坑。
- 修复方案：Windows 上 `--run` 自动改用 `powershell -File`（生成 ps1 到临时目录再执行），或检测到断言语言与执行器不匹配时直接提示并退出码 4。

### P2-2 README 与 CLI 参数不一致

- 现象：README 写 `--source`，实际参数是 `--from`
- 修复方案：改 README 或加 `--source` 别名。

## 四、亮点（值得保留的设计）

1. 三态 status + 退出码契约（equivalent/approximate/unsupported + 0/2/3/4）——agent 可分支处理，这是给 AI 用的正确姿势
2. drills 真机断言机制——"在目标机上自证"的理念远超同类工具，macOS/FreeBSD 侧已闭环
3. `prompt-export` 生成速查表注入 system prompt——省 token 的正确方向
4. JSON 契约稳定（schema:1），`kind` 字段标注命中路径，可观测性好
5. 数据格式（jsonc + flags 语义映射 + recipes + caveats）表达力足够，问题全在引擎层的匹配/替换策略

## 五、结论

数据资产（127 命令/249 写法）经真机验证质量可靠，Windows drills 9/9 全绿证明映射本身是对的；问题集中在**引擎的"槽位匹配 + 字面量回替换"策略**——这个设计在简单场景（`rm -rf build`→`build`）有效，一旦用户输入与示例值结构不同就静默失败，且失败发生在最危险的命令上。修复应优先做"替换失败必须降级告警"这一条不变量（P0-1/2/3 共同根因），再补数据映射。
